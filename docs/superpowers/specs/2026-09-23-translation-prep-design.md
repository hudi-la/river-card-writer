# 译前备料 · 设计文档

*日期：2026-09-23　·　状态：设计定稿，待写实现计划*

## 0. 一句话

作者用中文起稿、必须用英文成稿。这个功能**不产出译文**——它在作者动手写英文之前，把中文里那些**质感最重、最容易在英译中被压平的地方**挑出来，为每一处备好精确的英文词与语感差别，由作者自己写成句子。

（AI 的产出**不进 `en`**——成稿由中文和作者自己写的英文构成，提词存在旁边一份独立数据里，见 §9。放宽到什么程度由每份稿子自己的档位决定（两档，默认最严）。）

## 1. 缘起与定盘星

作者的困境：**很多稿子最终必须是英文，但没办法用英语起稿。** 直接的解法是让 AI 翻译整稿；这个功能最初的确是那么设计的，成文前被砍掉了。

**被砍掉的是那个工作流，不是"模型不许产出译文"，也不是"不许存 AI 的东西"。** 原设计是：AI 译 → **译文落进 `en`** → 作者在译文上润色。要命的是中间那一步：译文一旦占据了作者那个字段，**作者就从写作者变成了校对者**。§9 的 `auto` 档仍然能给整句译文，也照样会被存下来——但存在 `hints` 里当参考，`en` 始终空着等作者自己敲。这两件事看着像，实际是两回事。

砍掉那个工作流的是两条理由，一条外部、一条内部：

**外部**：有些接收方明确要求不可以用 AI 写东西。一份由 AI 译出、作者润色的稿子，作者将来无法坦然地说"这是我写的"。

**内部**（更重要）：它违背这个工具的定盘星——

> 不喂饭、不做捷径、**帮人做难的事，而不是绕过它**。

翻译不是那件难事的捷径吗？是的。而且它连带毁掉一件更值钱的东西：**作者的英文写作能力永远不会长。** 每译一次，就更依赖一次。

### 关键翻转：靶心是「精确点」，不是「难点」

设计中途作者给了一段自己的稿子，附上一份想要的输出示例，推翻了原本的地基。

原设计要模型「挑出难翻的地方」——它会去捞成语、文化专名、罕见搭配。

作者的示例挑的是**中文里已经很准的地方**：「凑」「蹭」「巡逻」「昂首挺胸」「踱步」「一爪子按下」。这些词**一点也不难翻**。难的不是翻不出来，是**会被压平成 walk / move / hit**。

所以模型该问的不是"哪里卡住了"，而是：

> **哪里的质感一旦丢了，这段就死了？**

这一条是整个功能的地基。写提示词时先回到这里。

## 2. 范围

**做：**

- 卡片级的中英并存：英文住在中文卡片里，你自己写。
- 中文改动后，自动知道哪一段英文失效了。
- 章级「备料」：生成这一章的靶心清单。
- 跨书的个人词汇记录，按**语义族**组织，强度会随时间衰减。
- 两档 AI 辅助（只给词 / 给整句译文），按稿子设，默认最严（§9）。产出存进 `book.hints`，**两档一律不进 `en`。**
- **语料查证层**：每个候选查真实语料频率，分「正常 / 罕用 / 未查证」三档显示（§11.1）。

**明确不做（YAGNI）：**

- **让 AI 的产出落进 `en`**——任何档位下，那个字段只装作者自己敲的字（§9.1）。
- 自动后台备料（你不按，它不动）。
- Batch API 半价批量处理。
- 句级 diff（"中文改在哪一句"）。
- 英文行内标记（斜体/引注/删除线）。
- 中译英以外的语言。属性就叫 `en`；将来真要第三种语言，那是一次改名迁移，不值得现在为它加一层容器。
- 正经的间隔重复算法、背单词卡。
- 自建语料库。查证走现成的 Ngrams 端点，不自己攒语料。
- 词形还原库（先用简单归一化，实测不够准再说）。

## 3. 核心模型：英文住在中文卡片里

卡片节点新增三个属性，跟现有的 `note` / `collapsed` 同一个模式：

| 属性 | 类型 | 默认 | 含义 |
|---|---|---|---|
| `en` | `string[] \| null` | `null` | 英文，每段一个字符串。`null` = 没写过 |
| `enSrc` | `string` | `''` | 写英文时那一版中文的指纹 |
| `enAt` | `string` | `''` | 最后一次改动英文的时间 |

**为什么英文是纯文本数组，而不是 ProseMirror 片段：**

因为段落一一对应（`en.length === 中文段落数`）。既然如此，英文**不需要自带段落样式**——章名、小标题、列表、引用、注，全部按序号从对应的中文段继承。

这一条决定连锁地消掉了整个方案里唯一有风险的部分：

- 不需要第二个 TipTap 编辑器、不需要派生文档、不需要写回桥、不需要防光标被冲掉。
- 并排不是"两个编辑器并列"，而是**每张卡自己是两栏**——`CardView` 里 `NodeViewContent` 旁边加一个 `<aside>`，卡片本身是两列 grid。于是只有一个滚动条，中英**天然永远对齐**，一行滚动同步代码都不用写。
- 写回走 TipTap 官方的 `updateAttributes({ en })`。
- 切分与合并变成数组的 slice 和 concat（§5）。

代价：英文里没有行内标记。接受。

**书级新增**：`book.translation = { brief, glossary[], reference? }`

- `brief` — 这本书的文体调性，让候选词的语域对得上。
- `glossary` — **你自己的定译**（川 → River）。清单遇到已定译的词，直接显示你的，不再建议。
- `reference` — **可比较的解法库**，不是文体样本。别的作家怎么处理同一种动作，以及那个解法和你的质感差在哪。（示例里的 Dillard「stick his skull under my nose」就是这个字段该装的东西：她的笨拙有力 vs 你的轻而亲。）

**同步几乎白拿**：`data` jsonb 里多一个 `translation` key；英文跟着 `doc` 走，`sync.ts` 一行不改。盒子里的卡是同样的 card JSON，所以英文跟着进盒子、出盒子也是自动的。

## 4. 「确认」是算出来的，不是存出来的

> **2026-10-02 换过语义。** 原来是"过期"：中文一变就断言"这段英文过期了"。
> 问题在于——**工具根本不知道英文还能不能用，它只知道中文的字节变了。那是在
> 断言一件它无从知道的事。** 而且无路可走：作者没有任何办法说"还合用"，
> 清掉标记的唯一途径是去改英文（`commit` 里的 `if (next[index] === text) return`
> 让空改动也不生效）。改一个错别字，英文就永远灰着。
>
> 现在记的是**作者认过没认过**——那是工具确实知道的事。"中文变了就撤销确认"
> 在逻辑上严丝合缝：作者当初认的是"这段英文配那一版中文"，那一版没了，认可
> 自然不再覆盖。这也更合 §1 的定盘星：工具不替作者判断对错，只记住他认过什么。

四个状态，全部由 `confirmState(en, enSrc, 中文)` 算出来，没有任何地方需要"记得改状态"：

| 状态 | 条件 | UI |
|---|---|---|
| `unwritten` | `en == null` | 占位「还没写」 |
| `unconfirmed` | 写了，`enSrc === ''` | **中性**：不报警、不涂灰，只给一个「确认这一段」 |
| `confirmed` | `enSrc` 与当前中文的指纹相符 | 左侧一条细绿线 + 「✓ 你确认过这一段」（可撤回） |
| `invalidated` | `enSrc` 非空但对不上 | 「中文改过，之前的确认已失效」+「重新确认」 |

**刻意不把未确认的英文涂灰。** 涂灰是在说"这东西有问题"，而工具并不知道它有没有
问题，它只知道作者还没认。未确认是中性状态。只有"认过、但中文又改了"才值得提
一句——那是作者自己的承诺失效了，不是工具的判断。

**确认章只由作者的点击盖上。**

- 写回英文（`commit`）**绝不**盖章——确认是作者的动作，不是打字的副作用。
- 改自己的英文**不**撤销确认：他是作者，修自己的字是在继续背书，不是推翻。
- 切分：原来确认过、且能对齐时，两半都保留确认（切一刀没改动任何一个字）；对不齐
  时一律退回未确认。
- 合并：**只有两边都确认过**才算确认。原来这里在两边都有英文时无条件盖指纹——
  在新语义下那等于系统替作者认了一次，是最不该发生的事。

## 5. 切分与合并：英文必须跟着走

**这不是可选项——默认行为是坏的：**

- `splitCard` 走 `tr.split()`，ProseMirror 会把节点属性**复制给新卡**。什么都不做 → 切完两张卡各扛一份完整英文，凭空多出一份重复译文。
- `mergeCardBackward` 走 `tr.join()`，join 保留**前一张**的属性。什么都不做 → 后一张卡的英文被静默吞掉，作者润色过的东西无声消失。

**合并 = 拼接。** `A.en ++ B.en`，指纹按合并后的中文重算，**保持新鲜**。接缝处可能略生硬，但那是一眼看得见、顺手能改的东西，远好过清零。只有当一边压根没写过英文时才标记过期——那份英文确实盖不全中文了。

**切分 = 在对应位置切开。**

- 光标在**段落边界**（`parentOffset === 0`）→ 英文在同一个段序号上切开，两半都**保持新鲜**。
- 光标在**段落中间** → 那段中文被劈开了，英文没有可靠对应切点 → 英文整份留给前半张，两半都标记过期。

前提是段落数一一对应，而这由数据形状本身保证（`en: string[]`，长度恒等于段落数）。另设一个校验器守在数据入口，格式不对的 `en` 绝不允许进文档——跟现有的 `isValidCover` 同一个路子。

## 6. 靶心：一个条目长什么样

模型对每个靶心产出五件事。**少一件，条目就废了一半。**

1. **中文原词/短语** + 它在哪张卡。
2. **你的中文为什么准。** 「凑 = 主动靠近但轻、试探；蹭 = 接触中带摩擦、带亲昵。」作者是凭本能写的；把本能说成话，后面的选词才有依据。**没有这一步，候选词只是同义词罗列。**
3. **笼统译法长什么样，以及它死在哪。** "its face was close to mine（凉的、死的，没有动作）"。**得先看见坏的，才感觉得到好的差别。** 这是整个条目里最教人的部分。
4. **2–4 个候选**，每个带**语域**（正式 / 口语 / 文学 / 罕用）和**语感差别**，并说明**为什么这一个贴**。（nuzzle 比 Dillard 的 stick 更轻更亲。）
   - **每个候选必须同时说出它丢了什么。没有任何候选可以只有优点。** 这是结构性约束，不是礼貌要求：第一轮试跑里模型说 self-effacement 是「最完美的术语级对应」——这种听起来像结论的背书比生造词更危险。要求每条都报缺点，结构上就不可能出现"这个是完美的"。
   - 每个候选还要附一个 **`verify_form`：用来查语料的裸词形**，供 §11.1 的查证层使用。**措辞要当心**：早期提示词里写的是「基本搭配形式」，模型据此产出了 `ridicule fame` 这类动词+宾语组合，直接导致四成好词被误标。规则见 §11.1 的误报陷阱。
5. **归进一个语义族**（§7）。

**第六种情况要诚实说出来**：英文没有对应单词。「昂首挺胸」就没有——只能用身体位置写（head high, chest out），或者换一个带喜剧感的近似（strut）。这本身是一类合法条目，不是失败。

### 6.1 靶心随文体而变

**这一条是拿两段真文字试跑之后加的，不是设计时想到的。**

用作者的两段真稿子各跑一次，发现靶心的类型几乎不重叠：

| 文体 | 力气在哪 | 靶心长什么样 |
|---|---|---|
| **叙事**（猫堵门那段） | **动词的质感** | 凑 / 蹭 / 巡逻 / 昂首挺胸 / 踱步 / 一爪子按下 → nuzzle / prowl / strut / pounce |
| **议论 · 学术**（Echo Chamber Realms） | **抽象概念的精确度**、语域一致性 | 讨好 / 羡慕 / 降低自身可见性 / 编写关系 → people-pleasing / envy·admiration / deference / script |

议论文里一个动词质感的靶心都没有。叙事文里也几乎没有语域问题。**所以模型不能只有一套找靶心的标准。**

**必须单独立一类：论点句（承重句）。** 一篇议论文里有一两句是全篇的支柱——Echo Chamber Realms 里是最后那句「并不直接编写三个角色之间的关系，而是构造关系得以发生的初始条件」。这类句子**译平一句，整篇就塌**，因为读者从此看不出这篇在主张什么。它的优先级高于其余所有靶心，在清单里要排最前、要标出来。

实现上先让模型自己判断文体（省一个交互），实测发现判不准再让作者手动标。

**靶心的分类**（让清单可分组、扫得快；带 ▲ 的是议论文专属）：

- 动作质感（最重要——作者的力气基本都在动词上）
- 成语与意象
- 文化专名
- 语域不对等
- **中文本身有歧义** ← 这一类不给答案，只告诉你"这里中文能有两种读法，英文必须选一种，你选哪个"。**那是只有作者能做的决定，而且正是把网压成线的那种活。**（试跑验证：「羡慕」——英文的 admiration 与 envy 之间没有中间项，作者必须先决定角色到底要什么。这一类立得住。）
- ▲ **承重句 / 论点句**——优先级最高，见 §6.1
- ▲ **抽象概念的精确对应**（讨好 / 退让 / 联结 / 认可）
- ▲ **学术语域的一致性**——同一个概念在全篇里不能换着词说

## 7. 词汇记录：按族存，会衰减

**跟人走，跨书共享。** 你的词汇是你的，不属于哪一本书。存 `cw_vocab`（owner 主键 + jsonb），与 `cw_universal` 完全同构——这不是新数据通路，是把已经走通过的那条路再走一次。

**按语义族组织，不是按词排列：**

```
『带气势的行走』 → patrol / prowl / stalk / strut
『轻柔的接触』   → nuzzle / brush / graze
```

**为什么：你想不起词的时候，想得起的是功能**——"我要一个形容猫得意地走的词"。按字母排的词表帮不了这个忙。而且**"你在哪个族上反复缺词"** 比"你忘了哪个词"有用得多：它直接告诉你下一步该补哪里。

每个词记四件事：用过几次、最近一次何时、被推过几次、最近一次推是何时。

**强度会衰减。** 早期设计把它当开关（用过 = 会了 = 不再推），作者一句话推翻了：「有的时候你给我推过的，我也会忘啊。」

**用过一次不等于会了。** 三个月前用过一次的词早就忘了；用了二十次的才真是你的。所以分数由次数和新近度共同决定：

- 用得多且近 → 不再打扰你。
- 用过一次又很久没碰 → 自动回到池子里，再递一次。
- **推过、而你始终没用过 → 必须接着推，并且明着标出「第 3 次给你这个词」。**

最后这条是刻意的。这条信息本身有价值：它告诉你，你反复在同一个地方伸手、反复落空。**一个安静喂词的工具会让你一直忘下去；一个告诉你"你又忘了"的工具才在帮你做难的事。**

## 8. 模型做什么，本地做什么

**这条分工线是设计里最要紧的一处，别在实现时模糊掉。**

**模型只做客观的那一半**：读这一章中文，找靶心，为每个靶心做 §6 那五件事。（`auto` 档下多产出整句译文——那是 §9.3 主动放开的部分，仍然只进边栏。）

**"你会不会"全部在本地算**：查术语表（定过的直接用你的）、查词汇记录（用得多且近的降权）、算衰减、标「第 N 次」、排序分组。全是纯函数。

三个好处：

1. **缓存前缀完全稳定**，每章备料很便宜。
2. **你的词汇史一个字都不出本机**，不进任何 API 请求。
3. 筛选逻辑随时可调，不用重新调教模型。

## 9. AI 的产出不进 `en`

### 9.1 三坨东西，存三份，但成稿只由两份构成

屏幕上同时有三样东西：

| | 存哪 | 进成稿吗 |
|---|---|---|
| **原中文** | `doc` 里的卡片正文 | 是 |
| **作者写的英文** | 卡片属性 `en`（§3） | 是 |
| **AI 提词** | `book.hints`，按 cardId 索引，**不在 `doc` 里** | 否 |

**提词是持久化的**——关掉再打开还在，备料一次反复用，不用重新花钱重算；回头还能翻当初给过哪些候选、当时为什么没选那一个。

**但它不在 `doc` 里**，这是刻意的：

- 正文 JSON 保持干净，导出成稿时天然不带提词，不需要额外的剥离逻辑。
- 提词条目可能比正文本身还长（一张卡五条靶心，每条五个字段），塞进 `doc` 会让每次编辑的 diff 和同步负载都被它主导。
- 提词跟中文一样会**过期**——它是为某一版中文算的。同一套指纹机制（§4）判定，不另起炉灶。

**这条线真正的内容是：`en` 这个字段只装作者自己敲的字。** 模型的产出无论哪一档、无论多长，都进 `hints`，不进 `en`。

**同时必须写明它保证不了什么**：`en` 干净，保证不了"这句话是作者写的"。一整段译文摆在边栏里，照着重打一遍，数据层看不出任何区别。**这两件事是分开的，实现时别把前者当成后者的证明。**

### 9.2 那条线在 `strict` 档是结构性的

`strict` 档下，模型收到的任务根本不是"翻译"，是"从这段中文里挑靶心、做词典条目"。它拿不到"请给出译文"这个指令。

**更强的一道保障在数据形状里：条目的 schema 里没有任何句子形状的字段。** 早期草案里有一个"通用例句"字段，v1 砍掉了——它是整个条目里最接近"替作者写句子"的地方，而 §6 的语感 + 缺点两个字段已经把它的作用扛下来了。**没有字段可以装句子，模型就没有地方放句子**，这比写一条"不许给例句"的规则可靠。返回值校验再兜一层：任何字段里出现完整句式一律拒收。

`auto` 档是主动放开这条线，不是意外漏掉——而且只放开一个字段。

### 9.3 两档

`book.aiPolicy: 'strict' | 'auto'`，**默认 `'strict'`**。

| 档位 | 边栏里出现什么 | 放开了什么 |
|---|---|---|
| `strict`（默认） | 词、语域、语感差别、笼统译法对照、范例作家的解法 | 什么都没放开，句子全由作者从白纸上搭 |
| `auto` | 加一段整句译文 | 整句是 AI 给的 |

> **原本还有一档 `open`「加骨架」**（给带空格的句法骨架让作者填词）。实现阶段作者
> 明确要求砍掉，只留两档：`给译文` 做成真开关，`加骨架` 不做。理由成立——骨架是
> 介于两者之间的半成品，它既不像 `strict` 那样守得住线，又不如 `auto` 有用。
> 少一档也少一份要维护的提示词分支。

**这道口子是分档位守住的，不是靠自觉：**

- `strict` 档的提示词里**没有**任何关于译文的说明，条目 schema 里**没有**能装句子的字段。
- 校验器按档位工作：`strict` 档下模型若夹带 `translation`，**拒收**——不是忽略、是拒收，作者会看到明确的错误而不是悄悄被塞进来。
- 就算在 `auto` 档，条目的 `nuance` / `loses` / `why_fits` 里**仍然不许出现整句英文**；句子只能待在 `translation` 那一个字段里。线上实测：auto 档跑出来 7 条靶心，条目字段里夹带整句的 0 处。
- **两档下译文都不进 `en`。** `en` 只装作者自己敲的字（§9.1）。

### 9.4 开关必须贴在稿子上

存在书上（`book.aiPolicy`），跟着书走——备份、导出、换设备同步过去，那本书还是那一档。新建的书一律 `strict`：**安全的那一档是默认值，放开要主动开口。**

UI 上要**一直看得见**：书名旁一个标记，提词边栏顶上再重复一次。**不要做成设置页里一个复选框。**

理由是这个开关**设错了不会报错**。全局开关的失败长这样：两个月前为了写博客调到 `auto`，早忘了；今天给禁 AI 的接收方交稿，没有任何东西会提醒。等发现的时候稿子已经在对方手里，而你正是那个说过"这是我写的"的人。这类错误没有第二次机会，只能靠**让状态一直在眼前**来防，防不了靠记性。

（第二道保险：`strict` 档的产出里**根本不会有骨架和译文那两块**，所以从边栏内容本身也能反推当前是哪一档。）

## 10. 界面

**布局是「两栏 + 一条边栏」，不是三栏。**

- **中文栏 | 英文栏** 并排，按卡对齐（由 §3 的 grid 结构保证，零滚动同步代码）。这两栏是反复比对的主力，必须保住可读宽度。
- **右侧固定边栏**显示**光标所在那张卡**的提词。位置固定，眼睛不用找；提词再长也撑不散河流。顶上挂当前稿子的 `aiPolicy` 标记（§9.4）。
- **为什么不做真三栏**：三栏等宽后每栏只剩三四十字宽，中文英文都变得难读——而牺牲的恰恰是最该保的那两栏。
- **章级「备料」按钮** → 一次把整章的靶心算出来，边栏随光标翻页。你可以先通读一遍再动手。**这不是第二个功能，是同一份提词的两种看法。**
- **过期**：英文那一段发灰，卡角一个小记号。**不弹窗、不打断、不催。**
- **收起中文**：中文栏可收窄到看不见，剩一条干净的英文河从头读到尾。英文在节点视图里而不在可编辑主体里，所以收起后照样能改。
- 你敲进英文栏的词自动计进词汇记录。

## 11. 调用通路

**Supabase Edge Function 薄壳。** 拼提示词、校验返回值的纯函数放 `src/` 里正常测；Edge Function 只负责收 HTTP、加 key、转发。网络那层薄到不值得测。

**为什么是 Edge Function**：站点公开部署在 `card-writer.pages.dev`，API key 绝不能进前端 bundle。Edge Function 默认验 Supabase 登录态，key 放 Supabase secrets。它**不碰现有的 wrangler 部署流程**（代价：部署多一条 `supabase functions deploy` 的手动步骤，需写进部署笔记）。

> 已存在的 `user_secrets` 表（0 行，阅读陪伴那边的）可能是现成的密钥存放模式，实现时先看一眼再决定要不要沿用。

**模型**：默认 `claude-opus-5`，结构化输出锁住条目形状。

`strict` 档**不需要流式**——输出是清单不是稿子，又短又便宜。`auto` 档要整章译文，输出量是另一个量级，**这一档得走流式**，否则会撞 HTTP 超时。实现时按档位分流，别一刀切。

**供应商必须可换。** Edge Function 里模型调用独立成一个模块，换一家是改几十行的事。这个任务的评判标准高度主观，唯一有意义的测试是拿真实章节跑一遍，看捞出来的靶心是不是作者真的想要的。用量很小（一章一份清单），成本不是决定因素。

### 11.1 语料查证层（v1 必做）

**这一节原本写着"以后再说"。第一轮真跑就撞上了那个风险，作者也明确要求不能出错，所以它进 v1。**

风险是确定存在的：LLM 会造出流利但没人真那么说的英文搭配。第一轮试跑产出了 `cerebral haughtiness`（没人这么写）和 `architecting the initial conditions`（architect 作动词是商业黑话）。对一个"帮你选词"的工具这是最坏的失败——作者信了、写进稿子、交出去。

**对策不是要求模型自觉，是在本地查证。** 用 Google Books Ngrams 查每个候选的真实语料频率——那是统计，不是模型判断，生造的词没地方躲。实测两个坏词全部被抓住，十个好词全部通过。

**查证只回答一件事：这个词组在真实英文里有没有人用过。不回答"常不常用"。**

> **2026-10-02 砍掉了频率判断。** 原来还有一档「罕用」（频率低于 1e-8）。作者
> 一句话点破了那是方向错误：**学术和文学写作里，精确的词往往就是低频的词**
> ——`operationalized`、`enmeshed`、`self-effacement` 全都不常见，全都是对的。
> 给它们挂一个像警告的标签，等于在惩罚精确。
> 常不常用这件事由候选自己的**语域**字段来说——那是人话判断，不是一个数字。

| 档位 | 含义 | 显示 |
|---|---|---|
| `found` | 语料里有人这么用 | 最轻的徽章。这是常态，不该抢眼 |
| `collocation-unseen` | 词本身有，但这个组合没见过 | 标出来。**不能并进 found**——对"造搭配"最敏感的恰恰是这一档 |
| `not-found` | 整体和词头都没查到 | 降级显示 + 删除线。**只有这一档值得警惕** |

一个只在真有问题时才响的信号才有人看。原来「罕用」几乎条条都响，那是让作者
学会无视徽章的最快办法。

**能保证的边界要说清楚**：保证不了模型不再生造词，也保证不了捞全每个靶心。**能保证的是——未查证的词绝不和已查证的词长得一样。** 目标不是"不出现坏建议"，是"坏建议绝不能看起来像好建议"。

**误报陷阱——这是查证层最大的坑，实测量化过，别低估它。**

查什么词形，结果差好几个数量级。第二轮试跑里模型给出的 26 个 `verify_form`，**10 个在语料里查不到**，而它们几乎全是假警报：`ridicule`、`scoff at`、`lampoon`、`engineer`、`curate` 都是再正常不过的英文词。原因是模型把 `verify_form` 写成了「动词 + 宾语」（`ridicule fame`、`curate initial conditions`），那种组合当然不会作为 5-gram 出现。

改成查**裸词形**后，13 条全部修好：

| 模型给的 | 结果 | 改成 | 结果 |
|---|---|---|---|
| `ridicule fame` | 查不到 | `ridicule` | 2.5e-6 |
| `script relationship` | 1.1e-10 | `script` | **1.3e-5**（差五个数量级） |
| `practice self-effacement` | 6.8e-11 | `self-effacement` | 8.5e-8 |
| `maintain low profile` | 1.6e-10 | `maintain a low profile` | 2.3e-8 |

**为什么这条必须写死**：不修的话查证层会把约四成好候选标成「未查证」。徽章一旦变成噪音，作者两天就学会无视它——**那比没有徽章更糟**，因为整个价值主张就是"未查证的词不会看起来像已查证的"。**一个会误报的查证层不是半个保障，是负资产。**

规则（已写进提示词，附正反例）：`verify_form` **只写候选自己的词，不加宾语、主语或上下文**；用原形；固定习语要完整、包括冠词（`maintain a low profile` 而非 `maintain low profile`）；≤5 词，越短越好。判据是：单独拿去搜英文书应该能搜到大量结果；如果它只在那个造出来的语境里成立，就是写错了。

**查证层必须诚实标出自己的三个盲区**，否则它会变成新的权威来源：

1. **Ngrams 最多 5 个词**，更长的短语根本查不了。
2. **语料截止 2019**，**系统性低估新词**——`people-pleasing` 只有 2.05e-8，明显低于它真实的当代使用度。一个词可能仅仅因为"新"就被标成可疑。
3. **只有书面语料**。对本用途其实是优点（学术、文学语域覆盖得好），但口语/网络用法测不到。

实现成本不高：每个候选一次 HTTP，**结果可永久缓存**（一个词的历史语料频率不会变）。是非官方端点，要有取不到时的降级路径——取不到就一律显示为「未查证」，绝不默认当作已查证。

## 14. 待定：英文的分段权

**状态：作者正在用真稿子评估，暂不改动（2026-09-30）。**

### 约束

`en.length === 中文段落数`，锁死。作者改不了英文的分段。

### 它买到了什么

1. **英文不用自己存段落样式**——章名、小标题、列表、引用全部按序号从对应的中文段继承。这是当初消掉"第二个编辑器 + 派生文档 + 写回桥"那一整坨复杂度的关键（§3）。
2. **切卡时英文能按序号跟着切**（在段落边界下刀时，§5）。
3. **两栏逐段对齐**，能一段对一段地比。

### 它收走了什么

**英文的分段权。** 而中译英里重新分段是常规操作——中文段落通常更短，英文（尤其学术文体）常要把两三段并成一段；有时还需要加一个中文里没有的过渡段或主题句。

更要紧的是：**分段本身就是写作。** 这跟 §1 的定盘星冲突——"帮人做难的事，而不是绕过它"。这条锁不是在帮作者做难的事，是**替他做了一个本该他做的决定**。这是设计违背了自己的原则，不是用法有问题。

### 三条出路

| | 做法 | 代价 |
|---|---|---|
| **A** | 松绑段数，但保留逐段格子：仍是一段一格，可增删格；中英段数相等时照旧逐段对齐、样式照旧继承，一旦不等就不再声称逐段对应、降级成按卡对齐 | 多一个增删段的操作；段数不等时英文样式只能退成正文 |
| **B** | 整卡一个输入框，空行分段，完全自由 | 逐段对齐和段落样式继承全没了，两栏只能按卡对齐 |
| **C** | 保持现状 | 作者改不了英文分段 |

实现成本：A 大约 1–2 小时。`isValidEn` 去掉长度相等的判断；`CardView` 按 `en.length` 而不是中文段数渲染格子，并加增删格的入口；`splitEn` 本来就以"两边段数相等"为对齐前提，**自动降级、不用改**；提示词仍然要求模型输出 1:1（那是个好默认），只是作者不再被锁住。

### 评估时该盯什么

作者用真稿子跑一阵，判据不是"别扭不别扭"，而是：**有没有真的遇到过一段中文必须拆成两段英文、或两段中文必须并成一段英文的地方？** 如果有，是偶尔还是常态。有些约束听着难受、用起来反而无所谓；这一条到底属于哪种，只有真稿子能回答。
